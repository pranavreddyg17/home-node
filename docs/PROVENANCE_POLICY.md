# Protected provenance policy

The installer accepts an independently reviewed local JSON policy through paired
`--update-provenance` and `--update-provenance-sha256` arguments. Establish the
SHA256 and signer identities through the trusted release setup process. A digest
or key copied from the downloaded provenance envelope does not establish trust.
The input is a no-follow regular file, bounded to 16 KiB. The exact bytes are
journaled at `/etc/homenode/update-provenance.json`, root-owned mode `0400`.

Schema one requires exactly these fields:

| Field | Required value |
| --- | --- |
| `schema` | Integer `1` |
| `threshold` | Integer from `2` through the number of distinct keys |
| `keys` | At most 16 distinct Ed25519 public keys, each 64 lowercase hex characters |
| `builderId` | Independently approved builder identity, 1–2048 bytes |
| `buildType` | Independently approved SLSA build type, 1–2048 bytes |
| `externalParameters` | Exact reviewed JSON object for the build |
| `sourceUri` | Exact reviewed source dependency URI, 1–2048 bytes |
| `sourceCommit` | Exact reviewed 40- or 64-character lowercase hex source commit |

Duplicate decoded JSON keys, casing aliases, missing/unknown fields, trailing
values and ambiguous parameter objects refuse. Identifiers are exact strings;
the parser does not establish their real-world ownership or qualify a builder.
External parameter values must match structurally, including JSON types and
numeric representations. Matching source URI must occur exactly once in resolved
dependencies with the expected `gitCommit` digest.

Installer acquisition verifies DSSE signatures from at least the configured
number of distinct pinned keys over the exact in-toto payload bytes. An envelope
`keyid` cannot establish signer identity or count a second key. The authenticated
Statement/v1 must use SLSA provenance/v1 and bind exactly one subject to the
retained package SHA256. Package identity and protected policy are checked again
before success. Inspection staging independently repeats this qualification;
a failure exposes no acquired package or starts no inspection publication.

The policy pins one reviewed source commit and parameter set. It cannot authorize
arbitrary future releases. Journaled policy replacement, key rotation/revocation
and production promotion are unfinished; editing the owned file directly causes
an ownership conflict. Do not loosen the policy to bypass that conflict.
Authentication does not establish SBOM completeness, vulnerability status,
migration correctness, safe rollback or owner approval. Those remain separate
required gates before installation. No production signing keys are generated by
installation preparation.
